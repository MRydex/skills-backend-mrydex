# Claude Code Project Guidelines

## Backend / .NET Stack Conventions
This project enforces the official **.NET 10 backend** standards in [`skills/desarrollo-backend-buenas-practicas/SKILL.md`](./skills/desarrollo-backend-buenas-practicas/SKILL.md) (or `~/.claude/skills/desarrollo-backend-buenas-practicas/SKILL.md`). Read `SKILL.md` first; then read only the reference that matches the task (paths relative to the skill folder):

- **Architecture and size** (`references/01-solution-structure.md`): Clean Architecture (Api → Application → Domain; Infrastructure implements Application interfaces). Onion only when the domain has its own rules or more than one host uses it (§1.5); an existing repo keeps the shape it has. One class per file. Max 150 lines per controller or handler, 250 per repository, 300 per class, 40 per method.
- **C#** (`references/02-csharp-design.md`): primary constructors, records, real nullable, `async` all the way. Never `.Result`, `.Wait()` or `async void`.
- **Controllers** (`references/03-controllers.md`): thin. One action = receive the request, `await mediator.Send(request, cancellationToken)`, map to `ActionResult`. Every action has `[RoleAuthorization(...)]` and real `[ProducesResponseType]`.
- **Mediator** (`references/04-mediator-handlers.md`): team mediator (`IRequest<T>` / `IRequestHandler<TRequest,T>`), never MediatR. Handlers are `internal`. Contract types: `<Action><Entity>Request` in, `<Entity>Response` out, same names as the TypeScript front, no `Dto` suffix; project straight to the `Response`, no AutoMapper (01 §1.2).
- **Data access and cache** (`references/05-data-access-dapper.md`): Dapper with `const` SQL, explicit columns, parameters only, `CommandDefinition(transaction:, cancellationToken:)`. Writes through `IUnitOfWork`. Cache as a Scrutor decorator.
- **EF Core / LINQ** (`references/15-data-access-ef-core.md`): only in repos that already have a `DbContext`. `AsNoTracking` + `Select` to the `Response`, async with `CancellationToken`, no N+1, `IQueryable` never leaves the repository, `FromSql` interpolated (never concatenated), one `SaveChangesAsync` per handler via `IUnitOfWork`, idempotent migration scripts (never `Database.Migrate()` at startup).
- **Validation** (`references/06-validation.md`): `AbstractValidator<TRequest>` + `Guard.AgainstInvalidSpecification` as the handler's first line.
- **Errors** (`references/07-errors-responses.md`): typed exceptions + `IExceptionHandler` → `ProblemDetails`. Never `BadRequest("text")` or `ex.Message` to the client.
- **Config and secrets** (`references/08-configuration-di-secrets.md`): Options pattern with `ValidateOnStart`; secret values only in Azure Key Vault (environment variables only where there is no Key Vault, §8).
- **HTTP integrations** (`references/09-http-integrations.md`): typed `HttpClient`, explicit timeout, Polly only for transient errors. Never disable certificate validation.
- **Logging and tests** (`references/10-logging-tests.md`): never log tokens, connection strings or PII. xUnit + Moq, `<Method>_When<Condition>_Should<Result>`. Before "done": `dotnet build` without new warnings; from medium risk, `dotnet test` of the UnitTest project green (§13.3).
- **Security, always** (`references/11-security.md`): every change passes the Red Team review (§11.1). Dependency audit with `dotnet list package --vulnerable --include-transitive` when starting, after any package change and before delivering if the task touched packages; flag `High`/`Critical`, never bump a major version without asking (§11.4). Report every vulnerability found, even out of scope. **When asked for security** ("audit security", "is it safe?"; a bare "audit this" also runs the quality pass of §13.10): run §11.6, which reviews every security area (each one OK / finding / N/A) and goes deeper with that area's skill (`offensive-*`, Anthropic-Cybersecurity-Skills, Cloudflare `security-audit`, `claude-security`) where there is a finding, the area is sensitive or the scope is large.
- **Known tech debt** (`references/12-tech-debt.md`): never copy it into new code, never fix it out of scope; report it in one line.
- **Workflow** (`references/13-workflow-orchestration.md`): explore before editing, plan in `tasks/todo.md`, no scope creep, no over-engineering (§13.7.1), AI files in `.gitignore` (§13.9).
- **Checklists** (`references/checklists.md`): run through them before delivering.

## Agent Efficiency (always on)
See `references/14-agent-efficiency.md`.

- **Adapt to the agent and models in use**: Model and tool names in the skill (Opus, Haiku, `/compact`, `AskUserQuestion`) are examples. Detect which agent and models are available and use the equivalent. Rules never change, only syntax (§14.7).
- **Caveman mode**: Terse replies, no filler. One short status line when starting a new phase or before a long-running step. Technical terms, code and errors exact. Normal prose for security warnings, irreversible actions, step sequences where compression makes the order ambiguous, when the user asks for clarification, and in code, commits, PRs and docs.
- **Library lookups**: Before researching a library (`Corp.*` private feed or public NuGet), check for another open agent session (`ListAgents`) that knows it and ask it (`SendMessage`). Then code in the repo that already uses it, then docs MCP, then XML docs in `~/.nuget/packages`, then web. `Corp.*` has no public docs: no MCP or web; if that is not enough, ask the user.
- **Orchestrate, delegate only when it saves tokens**: The selected model plans, decides and always reviews. Delegate to the team subagents (`investigador`, `ejecutor-backend`, `revisor-checklist-backend`; if missing, an installed compressed equivalent such as `cavecrew-*`, else `Agent` with a cheaper `model`) large searches/reads (3+ files, logs, `dotnet build` / `dotnet test` output, docs) and mechanical edits across 8+ files, in parallel when independent; do small tasks yourself (§14.3.4). For a codebase-wide change that splits into 5+ independent units, propose `/batch <instruction>` (one background subagent per unit, each in its own worktree). Shared context in `tasks/brief-<task>.md`. Executors never guess: when stuck they return `NECESITA_ADVISOR: <question>`. Native advisor: off by default (Anthropic measured that no pairing clearly beats the executor alone; a same-tier advisor measured 10x cost and widened scope). If the user enables it (`/advisor fable`), call it after orienting, when stuck and before declaring done; never for mechanical steps. Subagents without their own `model` run on Sonnet (`CLAUDE_CODE_SUBAGENT_MODEL`); use the team `Explore` (Haiku) for cheap searches. Briefs carry only the compact skill rules that apply (§14.3.5). Before compacting, add the 5-line session summary (goal, findings, done, next, files) to the `tasks/todo.md` Log (§14.4).
- **Ask upfront**: Before non-trivial work, ask all questions that change the result in one turn, with options and a recommended one (`AskUserQuestion`): endpoint contract, required role, target table/SP, cache yes/no. Do not ask what the repo already answers.
- **Working loop**: state the assumptions you made without asking in one line. Before coding each task, define a done-check you can run (test, build, request), and finish only when it passes. When two sources disagree (request vs skill, two instruction files, code vs docs or SP), show both and ask; never pick one silently. Let commands answer what commands can (`graphify query`, grep, compiler, `dotnet test`). Report passed / failed / skipped test counts: "tests green" is false if any were skipped. Judge warnings and tests by new failures only. Tests assert the business intent, not the mock setup; E2E and tests against real services run only when the user asks (§10.2). After 3 failed fixes of the same error, stop and report the blocker with the exact error. When resuming, check the `tasks/todo.md` Estado against `git log` and `dotnet build` first (§13.2, §13.3, §13.6). In the final report, list the decisions you made that the request did not fix, and say what each passing check covered and what it did not. Record every user correction in `tasks/lessons.md` and read it at session start (§13.8).
- **Classify and review by risk**: Read-only requests stay read-only. Classify: small if it can be resumed from the request plus `git diff` (work inline); large otherwise (`tasks/todo.md` with L1 = verbatim request, Specs, Tasks with risk, Log; one task at a time; commits of ~400 lines). Review by risk: trivial (no behavior change: text, comments, formatting, mechanical rename) = diff + `dotnet build` + §11.1 questions, medium (everything else) = + `ponytail-review` (+ `dotnet test` if there is a test project), high (auth/JWT/permissions, secrets, SQL DDL/migrations, data deletion, `Program.cs` pipeline, `.csproj` packages) = + independent reviewer + deep offensive review with the area's skill (§13.2, §13.3, §11.6). Delegate only for a named reason: big exploration, parallel writers, context backstop, verifier of a high-risk task or of a large diff (3+ files) against the checklist; when in doubt, work inline (§14.3.4).
- **Auto-compact**: At the end of each phase or before an unrelated task, save state to `tasks/todo.md` and suggest the user run `/compact` with focus (keep decisions, touched files, pending items); you cannot run it yourself. Before an unrelated task, suggest `/clear` instead. Never mid-change or with a pending question.
- **Graphify (no ceremony)**: no startup or closing command; the git `post-commit` hook keeps the graph current. Search by name (symbol, file, literal text) with grep / Glob directly. `graphify query "<question>" --budget 800` only for a flow question with no known name, running `graphify update .` right before it, and back to grep if it returns unrelated nodes. Measured (§14.5): `grep -l` cost 10 to 120 times less than a graph query, also in a 12,600-node repo; `graphify update .` takes 17 s there, so it runs only before a query. If it fails (`command not found`, `Rebuild failed`, `worker failed`), report the exact error; fixes in §14.5.
- **Agent tools (always)**: ponytail (minimal code, `ponytail-review` on the diff for every non-trivial change, §13.3); agent-skills by phase; per area, the matching external skill from §14.9 (repo rules win); `claude-automation-recommender` (claude-code-setup) once in repos without setup. Security scan: the `claude-security` plugin; per-surface hardening: the matching `offensive-*` skill (claude-red), only against the project's own code (§11.6). If one is missing, install it and say so in one line (§14.8).
